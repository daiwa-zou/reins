takeaway: Large tool libraries fail on context cost, intermediate-result bloat and parameter errors, and each has a distinct fix. Defer tool definitions behind search, let the model write code that calls tools so intermediate data stays out of context, and add concrete usage examples to schemas. Choose the feature by measuring which bottleneck you actually have rather than enabling everything.
---

## Learnings
- Agents will need hundreds or thousands of tools (IDE assistants: git, files, package managers, tests, deploy; ops coordinators: Slack, GitHub, Drive, Jira, databases, many MCP servers). Tool definitions plus results can eat 50K+ tokens before the agent reads a request.
- Natural-language tool calling costs one inference pass per call and accumulates intermediate results in context, and JSON schemas express structural validity but not usage patterns. Three complementary beta features address this (beta header `advanced-tool-use-2025-11-20`).
- Tool Search Tool, the cost: GitHub 35 tools (~26K tokens), Slack 11 (~21K), Sentry 5 (~3K), Grafana 5 (~3K), Splunk 2 (~2K) = 58 tools, ~55K tokens before conversation; Jira alone ~17K; Anthropic saw 134K tokens of definitions before optimization.
- Failure modes at scale: Claude picks the wrong tool among similar names (`notification-send-user` vs `notification-send-channel`) or passes wrong parameters.
- Tool Search mechanism: all tools are sent to the API but those marked `defer_loading: true` are not in the prompt. Claude sees the search tool (`tool_search_tool_regex_20251119`; BM25 also built in; custom variants such as embeddings supported) plus non-deferred tools, and search returns references that expand into full definitions (searching "github" yields only `github.createPullRequest`, `github.listIssues`).
- For MCP, use `mcp_toolset` with `mcp_server_name`, `default_config: {defer_loading: true}` and per-tool `configs` overrides (e.g. keep `search_files` loaded). Prompt caching is preserved because deferred tools enter only after a search.
- Tool Search numbers: traditional ~72K for 50+ MCP tools (~77K total before work, 122,800 tokens of window left); with search ~500 tokens upfront plus 3-5 tools (~3K), about 8.7K total (191,300 left), an 85% reduction that preserves 95% of the window.
- Tool Search accuracy on MCP evals with large libraries: Opus 4 49% to 74%; Opus 4.5 79.5% to 88.1%. Use it when definitions exceed 10K tokens, selection errors appear, multiple MCP servers are connected, or there are 10+ tools; skip it with fewer than 10 tools, when all tools are used every session, or when definitions are compact.
- Programmatic Tool Calling (PTC), the problems: context pollution (a 10MB log loaded when only error frequencies matter) and inference overhead (five sequential tools means five passes plus manual parsing).
- PTC mechanism: Claude writes Python that calls tools as functions inside a sandboxed Code Execution tool (`code_execution_20250825`); the sandbox pauses for tool results, and loops, conditionals, transforms and error handling are explicit code.
- PTC flow: add the code_execution tool and set `allowed_callers: ["code_execution_20250825"]` on opt-in tools (the API converts them to Python functions). Claude emits a `server_tool_use` block with `input.code`, tool requests arrive as `tool_use` blocks with a `caller {type, tool_id}` pointing at the `srvtoolu_` id, results go to the code environment and not Claude's context, and only final stdout returns as `code_execution_tool_result`.
- Worked example ("Which team members exceeded their Q3 travel budget?" with `get_team_members`, `get_expenses`, `get_budget_by_level`): traditional means 20 expense calls and 2,000+ line items (50KB+) in context; PTC uses `asyncio.gather` parallel fetches, a budget lookup, and prints only over-budget people, shrinking ~200KB raw to ~1KB.
- PTC gains: average tokens 43,588 to 27,297 on complex research (37% reduction); 19+ inference passes eliminated in a 20-call workflow; internal knowledge retrieval 25.6% to 28.5%; GIA benchmark 46.5% to 51.2%. Claude for Excel uses PTC for sheets with thousands of rows.
- Use PTC for large datasets needing aggregates, 3+ dependent calls, filtering or transforming before Claude sees data, intermediate data that should not bias reasoning, and parallel operations across many items (e.g. 50 endpoints). Skip it for single simple calls, tasks where Claude must reason over every intermediate, and small quick lookups.
- Tool Use Examples: a `create_ticket` schema (title, priority enum, labels array, nested reporter/contact, due_date, escalation) leaves open date format, ID convention (UUID vs `USR-XXXXX` vs bare numbers), when to populate nested objects, and correlations such as escalation and priority. An `input_examples` array alongside `input_schema` fixes this.
- Three examples teach YYYY-MM-DD dates, `USR-XXXXX` ids, kebab-case labels, nested patterns, and optional-parameter correlations (critical bug gets full contact plus tight-SLA escalation; feature request gets reporter only; internal task gets title only). Accuracy on complex parameter handling rose from 72% to 90%.
- Use examples for complex nested structures, many optional params with inclusion patterns, domain conventions schemas cannot capture, and disambiguating similar tools (`create_ticket` vs `create_incident`); skip for single-parameter tools, standard formats (URLs, emails), and constraints better expressed in JSON Schema. Examples cost tokens.
- Best practices: layer by bottleneck (context bloat gets Tool Search, large intermediate results get PTC, parameter errors get Examples; they compose). For search, use descriptive names and descriptions (`search_customer_orders` with a detailed description, not `query_db_orders` "Execute order query"), add system-prompt guidance naming capability categories, and keep the 3-5 most-used tools always loaded.
- For PTC document return formats precisely (field names, types, enums, timestamp format) and opt in parallel-safe, idempotent tools. For examples use realistic data rather than "string"/"value", vary minimal/partial/full, give 1-5 per tool, and focus on ambiguity not evident from the schema. Inspirations cited: Joel Pobar's LLMVM, Cloudflare's Code Mode, Anthropic's code execution with MCP.

## Harness implications
- Implement deferred tool loading natively: a small always-loaded core (3-5 hottest tools plus a search tool), everything else discoverable by regex, BM25 or embedding search over names and descriptions; expand only the matched definitions and keep the prompt-cache prefix stable.
- Treat whole MCP servers as toolsets with a default `defer_loading` and per-tool overrides; show in the UI which tools are loaded vs. deferred and how many tokens they cost.
- Provide a sandboxed code-execution channel in which tools are callable as functions and results bypass the model's context; only explicit stdout or returns enter the transcript. The UI should show code, the tool calls it made, and the summarized output as a collapsible group.
- Mark tools with metadata the harness needs for PTC: idempotent/parallel-safe, precise return-format docs; refuse to expose non-idempotent or destructive tools to code execution without permission gating.
- Support `input_examples` in the tool registry and lint for 1-5 realistic examples on tools with nested or many optional parameters.
- Make tool-definition token budget a monitored metric; alert when more than 10K tokens of definitions are resident and suggest deferral.
- Decide features by bottleneck with telemetry: track definition tokens, intermediate-result tokens, and parameter-validation error rates separately.
- Keep the system prompt listing capability categories so the agent knows what it can search for even when tools are deferred.
