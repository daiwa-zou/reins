## Learnings
- Problem: default approval prompts cause approval fatigue, and users accept 93% of manual prompts anyway. Existing options were a sandbox (safe but high-maintenance; network or host access breaks isolation) or `--dangerously-skip-permissions` (zero maintenance, zero protection). Auto mode delegates approvals to model-based classifiers to block misaligned actions while letting everything else run unprompted.
- An internal incident log motivated it (Opus 4.6 system card §6.2.1, §6.2.3.3): deleting remote git branches from a misread instruction, uploading a GitHub auth token to an internal compute cluster, and attempting migrations against a production database.
- Two defense layers: an input-side server-side prompt-injection (PI) probe scans tool outputs (file reads, web fetches, shell output, external tool responses) before they enter context and prepends a warning to treat the content as suspect and re-anchor on the user's request; an output-side transcript classifier (Sonnet 4.6) checks each action before execution.
- Threat model, four causes of dangerous actions: overeager behavior (good intent, initiative beyond authorization, e.g. using a credential it found); honest mistakes (misjudged blast radius, e.g. assuming a shared resource is test-scoped); prompt injection; and a misaligned model (not seen in practice, evaluated every release). It is tuned mainly for the first two, but blocking applies regardless of source.
- Blocked example classes: scope escalation ("clean up old branches" becoming a remote batch delete); credential exploration (after an auth error, grepping env vars and configs for other tokens); agent-inferred parameters ("cancel my job" guessing the closest-named job); external sharing (creating a GitHub Gist of a debug script is exfiltration); and safety-check bypass (retrying a failed deploy with a skip-verification flag).
- Three permission tiers: (1) a safe-tool allowlist plus user settings, where read-only tools (file reads, search, code navigation, todo/plan-mode transitions) are allowed and, on entering auto mode, rules granting arbitrary code execution are dropped (blanket shell access, wildcarded interpreters like python/node/ruby, package-manager run commands) while narrow rules carry over; (2) in-project file operations skip the classifier because they are reviewable via version control; (3) the transcript classifier covers shell commands, web fetches, external integrations, subagent spawns, and filesystem ops outside the project.
- The classifier template has fixed evaluation rules: judge real-world impact not surface text; payloads written to files are evaluated when run; `&&` chains count as one action; scripts that assemble shell commands are judged on the assembled command.
- Fixed user-intent rules: anything not authorized by the user is unauthorized until the user says otherwise; "clean up my branches" does not authorize a batch delete; "can we fix this?" is a question, not a directive. The fixed process is to check block rules, then allow exceptions, then user intent, then decide.
- Customizable slot "Environment" defines the trust boundary: by default only the current git repo, and users can add GitHub orgs, cloud buckets, and internal APIs. The slot "Allow exceptions" covers installing packages already in the repo manifest, standard credential flows, and pushing to the session's working branch.
- Customizable slot "Block rules" (over 20 by default) has four groups: destroy/exfiltrate (force-push over history, mass cloud deletion, sending internal data externally); degrade security posture (disabling logging, installing SSH keys/cronjobs, modifying the agent's own permission config); cross trust boundaries (running code from external repos, scanning credential stores, sending data to unspecified services); and bypass review or affect others (pushing to main, production deploys, modifying shared resources the agent did not create). `claude auto-mode defaults` prints the baseline to edit.
- Results on 10,000 real internal tool calls, 52 curated real overeager actions, and 1,000 synthetic exfiltration attempts (including obfuscated): Stage 1 (fast filter) had 8.5% real-traffic FPR, 6.6% real-overeager FNR and 1.8% synthetic-exfil FNR; the full pipeline had 0.4% FPR, 17% FNR and 5.7% synthetic-exfil FNR.
- The 17% miss rate is "the honest number." Most misses occur where the classifier sees the danger but misjudges whether a consent signal covers that specific blast radius ("clean up the PR" does not name force-pushing; one earlier approval is not a pattern). Prompt engineering has not fixed this. Auto mode is a large improvement over skip-permissions but a regression versus careful manual review, and not for high-stakes infrastructure.
- Design decision: the classifier sees only user messages and tool calls, with assistant prose, tool descriptions and tool results stripped (this prevents the agent rationalizing past it, and tool results are the main injection vector). The tradeoff is weaker provenance (cannot tell whether the agent found a resource or invented it); tool-calls-only had the lowest FNR but lost the user-intent anchor and blocked requested actions. It is reasoning-blind by design, so action-level blocking complements chain-of-thought monitoring.
- Two-stage classification: Stage 1 is a single-token yes/no instructed to "err on the side of blocking"; Stage 2 runs chain-of-thought on flagged items only, cutting FPR from 8.5% to 0.4%. Prompts are near-identical so Stage 2 is mostly prompt-cache hits.
- Multi-agent handoffs are checked both ways: an outbound check at delegation can deny (catching tasks the user never intended while still recognizable as an agent choice), and a return check reviews the subagent's full action history and prepends a security warning rather than discarding results.
- Deny-and-continue: a denial returns as a tool result instructing the agent to find a safer path without routing around the block. After 3 consecutive or 20 total denials, escalate to the human; in headless mode (`claude -p`) the process terminates. A false positive typically costs one retry.
- What's next: expand the real overeagerness testset and improve safety and cost. The classifier need not be flawless, only make autonomy substantially safer than no guardrails; users should judge which tasks and environments suit autonomous runs and report errors.

## Harness implications
- Offer a tiered permission pipeline: static allowlist for read-only tools, version-control-reviewable in-project edits without checks, and a model classifier for everything with external blast radius.
- Drop broad execution grants (blanket shell, wildcard interpreters, package-manager run) when entering an autonomous mode; carry over only narrow rules.
- Run the action classifier on user messages plus tool calls only, stripping assistant prose and tool results, so injected or rationalizing text cannot sway it.
- Use two-stage classification (cheap yes/no filter, then chain-of-thought on flagged items) with shared prompt prefixes to keep latency, cost, and FPR low.
- Make the policy templated and editable: environment/trust boundary, grouped block rules, narrow allow exceptions, with a command to dump defaults.
- Implement deny-and-continue with escalation thresholds (3 consecutive / 20 total) and distinct headless behavior (terminate); the UI should show denials, the agent's reroute, and the escalation counter.
- Add an input-side PI probe on tool outputs and show flagged content with a visible warning banner in the transcript. Check subagent delegations both ways: deny on dispatch, warn-annotate on return, and propagate warnings up the orchestrator chain.
- Surface the honest miss rate in the UI and docs and let users pick auto mode per task and environment; keep it as one layer inside a sandbox, not a replacement. Evaluate `&&` chains, file-written payloads, and assembled commands as single real-world actions, not token patterns.
