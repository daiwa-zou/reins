Make audit gaps and lesson ideas something the harness can research, build and re-verify from the UI, by turning "intake" into a general job type and finishing the lesson library it depends on. Work in a separate worktree of this repo; never use the checkout the dev server runs from as a run workspace (server edits restart it and kill live runs).

Context. A lesson's typed implications (`## Harness implications` bullets with a `[kind:target]` prefix and a verbatim quote) are the only link between lessons and the harness: `shared/implications.ts` derives the Harness cards, the "Lessons for this stage" blocks and the Ideas list from them. `docs/audit/<slug>.md` holds an independent audit per lesson (rows of learning, where, status implemented/partial/gap, then a `## Gaps` list with the smallest change for each) and is shown read-only. `server/src/intake/intake.ts` is a job type that borrows the engine loop (`AgentLoop` / `ClaudeCodeLoop`), runs one role (the librarian) with one terminal tool (`propose_lesson`) whose input is validated, then shows an approval card on the Stage and adopts the result; it has its own job files, status, cancel, duplicate detection and restart recovery, and never appears in Runs.

Do these in order. Each is a separate commit with tests; `npm test`, `npm run lessons:check` and the web build must pass at every commit.

1. Type the lesson library. 25 of the 30 bundled lessons have untyped implication bullets (195 in all; `npm run lessons:check` lists them). Give every bullet a `[kind:target]` prefix (component, stage, skill, foundation) and a `> quote` that appears verbatim in that lesson's Learnings, following the five lessons that are already typed and `docs/lesson-template.md`. Leave a bullet as a gap only when no existing component, foundation, stage or skill is what it is about. Done when `lessons:check` reports no "no [kind:target] prefix" warnings and every component and foundation is targeted by at least one implication.

2. Lift a job base out of intake, with no behaviour change. Move what is not lesson-specific (job file and status, id prefix and jobs directory per kind, start/cancel/list, events to the Stage, duplicate detection by input hash, resume after restart, the `check()` hook, the approval round trip) into `server/src/jobs/`, and make `IntakeOrchestrator`/`IntakeManager` the first subclass. A job kind declares: its role prompt, its tool allowlist, its terminal tool with a validator, its approval card kind, and what adopt writes. Existing intake tests pass unchanged; add tests for the base with a stub job.

3. Research job. Input: one audit gap (lesson slug + gap index) or one Ideas item (implication id). Role: a read-only researcher over this repo and the lesson library (file reads, grep, `list_lessons`, `read_lesson`; no writes, no shell, no network), so it needs no action approvals. Terminal tool `propose_findings`: what exists today with `path:line` citations, options, the recommended smallest change as a task statement the planner could take, and an estimate of scope. Validator: every cited path and line range must exist in the tree. Approval card shows the findings; adopt writes `$REINS_HOME/research/<gapId>.md` and the card offers "Start a run from this plan", which opens New run prefilled with the task statement and records the gap id on the run config. In the UI every audit gap row and every Ideas item gets a Research button and shows its research note and any runs that addressed it (run id and evaluation outcome) without changing the audit status.

4. Audit job. Input: a lesson slug. Role: an auditor with the same read-only tools, re-fetching the post with `http_fetch` (network allowed for this job only, as intake does). Terminal tool `propose_audit`: the rows and gaps in exactly the format of `docs/audit/<slug>.md`, with status per row. Validator: every `path:line` cited must exist; a row marked implemented must cite at least one. Approval card shows the diff against the current audit file; adopt overwrites it. Offer "Re-audit" on each lesson and, after a run started from a research note finishes, on that run's wrap-up card. The audit README totals must be regenerated from the files.

5. Retarget ideas inline. On an Ideas item, reuse the intake approval card's implication editor to set kind, target, domains and standing. Save as an override in `$REINS_HOME/lessons` (same slug overrides, as today), never editing a bundled file. `lessons:check` must still validate the override.

6. Delete user lessons. Add `DELETE /api/lessons/:slug` and a Delete control on the open lesson, for lessons in `$REINS_HOME/lessons` only: a bundled lesson gets 403 and no control (an override of a bundled slug can be deleted, which reveals the bundled file again). The confirm shows what the library loses: the Harness cards and stage blocks that drop a line, and whether any component or foundation is left with no implication targeting it. Delete removes the lesson file (and, for an adopted intake job, leaves its job directory with `source.md` and `draft.md` so the source can be taken in again; the intake duplicate check must no longer refuse that source). Remove an open research note or audit override that cites the slug only if it belongs to that lesson. The library picks the change up on the next request, as it does for a file removed by hand. Validate the slug the same way `GET /api/lessons/:slug` does and never follow a symlink.

7. One table. Put the audit status and the `where` citation on the implication itself (`Implication.audit?: { status, where, checked }`), populated by matching audit rows to implications by lesson and claim text, so the Harness cards, the Ideas list and the lesson view read one source. Keep `docs/audit/*.md` as the storage format for now; the audit job writes it and the loader joins it. Report in the lesson view any audit row that matched no implication and any implication with no audit row.

8. Replace the care profiles with Effort and Supervision. The Full, Minimal and Careful profiles mix two questions; split them into two controls on New run that each mean something to a person, and retire the profile picker and the Claude Code preset.

   Effort (low, medium, high, max) decides what the harness spends on the task. It sets the effort-tier components and the budgets: planner off/on/on/on; contract off/off/on/on; evaluator off/on/on/on, with max re-running every criterion; scouts off/off/on/on; fix rounds 0/1/2/3; turn and dollar budgets small/default/larger/largest. Put the exact table in `shared/components.ts` next to the catalogue so the docs table is generated from it.

   Supervision (unattended, check in at gates, ask before every write) decides the pauses and the guardrail mode: unattended is no pauses and auto mode with the action classifier on; check in at gates is the plan, contract and evaluation pauses with auto mode; ask before every write is every pause on and guardrail mode "ask", with the classifier off because nothing reaches it.

   Give every component a `tier`: `always`, `effort` or `engine`. Always-on components are the practices the lessons back and the audit marks implemented (progress notes, feature list, commit per phase, reset with handoff, compaction, context editing, self-verification, narration, stage lessons, project memory, tool hygiene switches such as tool search and examples); they are on at every effort, do not appear in New run, and a saved preset or a `POST /api/runs` body may not turn them off (400 with the component named). Effort-tier components (planner, contracts, evaluator, scouts, task budget, think tool) are set by the dial. Engine-tier components (the direct-only ones) follow the engine automatically and the config checker no longer needs to warn about them. The tier is a claim a lesson should back: the Harness card shows it, and `lessons:check` warns when an always-tier component is targeted by no implication with a bundled or reviewed standing.

   Keep ablation. The Harness panel's "run with/without" still works on always-tier components, labelled as an experiment, and a run started that way records `ablated: ComponentId[]` on its config and shows it on the title chip. That is the only path that turns an always-tier component off.

   The run composition becomes `{ effort, supervision, domains }` instead of `presets: ["careful", "golang", "cli"]`; migrate saved presets and old runs on read (full → medium + check in at gates; minimal → low + unattended; careful → high + ask before every write) and keep the old chip text for runs that predate the change. The title chip reads "High · Check in · Go · CLI". Domain recommendations (lesson `enables:`/`disables:`/`guidance:` and stage implications) still layer over the result but may only touch effort-tier and engine-tier components and may never lower effort or loosen supervision; a lesson may recommend an effort level for a kind of task as a tagged implication, shown on New run with its reason and never applied silently. Update `shared/config.ts`, `server/src/presets.ts`, the compose picker, the run header chip, `docs/configuring.md` and the README, and keep every existing composition test passing in its migrated form.

9. Budget in the unit that is real for the engine. On the Direct API engine usage is billed per token at list price, so a dollar budget is true. On the Claude Code engine usage counts against a Claude subscription, which is measured in tokens over a window, so a dollar figure is a list-price estimate that nobody pays; today Reins still passes it to the SDK as `maxBudgetUsd`, tells every role "$X of $Y remaining", and New run shows a dollar cap. Change the effort table to carry two budget columns, `budgetUsd` for the direct engine and `budgetTokens` for Claude Code (input plus output plus cache writes; cache reads counted at a tenth), scaled per effort level the same way. Resolve the active one from the engine when the run is created and record it on the config. On Claude Code: do not set `maxBudgetUsd` on the SDK; stop the run with "Token budget of N exhausted" when the counted usage passes the cap; the "Budget and time" line in each phase's first message says tokens and turns remaining, never dollars; New run shows a token field instead of the dollar field, with the note that usage counts against the subscription; the Overview gauge, the run header and the Reliability table show tokens as the budget measure and may show the estimated cost beside it labelled "estimated, not billed". On the direct engine nothing changes. Make `budgetUsd` an engine-tier setting so the config checker warns when a saved preset or a request body sets it for a Claude Code run, and migrate saved presets and old runs on read (an old Claude Code run keeps its recorded estimate as information). Tests: the token cap stops a scripted Claude Code loop; the prompt line has no dollar sign on that engine; the docs table gains the column and `docs.test.ts` stays green.

Done means: a user can open an audit gap, press Research, read the findings on the Stage, start a run from them in a worktree, watch it pass evaluation, press Re-audit on the lesson, and see the gap's status flip to implemented with a citation, all from the UI, with every step recorded as events and recoverable after a restart; and New run asks only for effort, supervision and domains, with every best practice on without a choice and every switch it does offer explained by a lesson.
