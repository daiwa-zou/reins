Make audit gaps and lesson ideas something the harness can research, build and re-verify from the UI, by turning "intake" into a general job type and finishing the lesson library it depends on. Work in a separate worktree of this repo; never use the checkout the dev server runs from as a run workspace (server edits restart it and kill live runs).

Context. A lesson's typed implications (`## Harness implications` bullets with a `[kind:target]` prefix and a verbatim quote) are the only link between lessons and the harness: `shared/implications.ts` derives the Harness cards, the "Lessons for this stage" blocks and the Ideas list from them. `docs/audit/<slug>.md` holds an independent audit per lesson (rows of learning, where, status implemented/partial/gap, then a `## Gaps` list with the smallest change for each) and is shown read-only. `server/src/intake/intake.ts` is a job type that borrows the engine loop (`AgentLoop` / `ClaudeCodeLoop`), runs one role (the librarian) with one terminal tool (`propose_lesson`) whose input is validated, then shows an approval card on the Stage and adopts the result; it has its own job files, status, cancel, duplicate detection and restart recovery, and never appears in Runs.

Do these in order. Each is a separate commit with tests; `npm test`, `npm run lessons:check` and the web build must pass at every commit.

1. Type the lesson library. 25 of the 30 bundled lessons have untyped implication bullets (195 in all; `npm run lessons:check` lists them). Give every bullet a `[kind:target]` prefix (component, stage, skill, foundation) and a `> quote` that appears verbatim in that lesson's Learnings, following the five lessons that are already typed and `docs/lesson-template.md`. Leave a bullet as a gap only when no existing component, foundation, stage or skill is what it is about. Done when `lessons:check` reports no "no [kind:target] prefix" warnings and every component and foundation is targeted by at least one implication.

2. Lift a job base out of intake, with no behaviour change. Move what is not lesson-specific (job file and status, id prefix and jobs directory per kind, start/cancel/list, events to the Stage, duplicate detection by input hash, resume after restart, the `check()` hook, the approval round trip) into `server/src/jobs/`, and make `IntakeOrchestrator`/`IntakeManager` the first subclass. A job kind declares: its role prompt, its tool allowlist, its terminal tool with a validator, its approval card kind, and what adopt writes. Existing intake tests pass unchanged; add tests for the base with a stub job.

3. Research job. Input: one audit gap (lesson slug + gap index) or one Ideas item (implication id). Role: a read-only researcher over this repo and the lesson library (file reads, grep, `list_lessons`, `read_lesson`; no writes, no shell, no network), so it needs no action approvals. Terminal tool `propose_findings`: what exists today with `path:line` citations, options, the recommended smallest change as a task statement the planner could take, and an estimate of scope. Validator: every cited path and line range must exist in the tree. Approval card shows the findings; adopt writes `$REINS_HOME/research/<gapId>.md` and the card offers "Start a run from this plan", which opens New run prefilled with the task statement and records the gap id on the run config. In the UI every audit gap row and every Ideas item gets a Research button and shows its research note and any runs that addressed it (run id and evaluation outcome) without changing the audit status.

4. Audit job. Input: a lesson slug. Role: an auditor with the same read-only tools, re-fetching the post with `http_fetch` (network allowed for this job only, as intake does). Terminal tool `propose_audit`: the rows and gaps in exactly the format of `docs/audit/<slug>.md`, with status per row. Validator: every `path:line` cited must exist; a row marked implemented must cite at least one. Approval card shows the diff against the current audit file; adopt overwrites it. Offer "Re-audit" on each lesson and, after a run started from a research note finishes, on that run's wrap-up card. The audit README totals must be regenerated from the files.

5. Retarget ideas inline. On an Ideas item, reuse the intake approval card's implication editor to set kind, target, domains and standing. Save as an override in `$REINS_HOME/lessons` (same slug overrides, as today), never editing a bundled file. `lessons:check` must still validate the override.

6. One table. Put the audit status and the `where` citation on the implication itself (`Implication.audit?: { status, where, checked }`), populated by matching audit rows to implications by lesson and claim text, so the Harness cards, the Ideas list and the lesson view read one source. Keep `docs/audit/*.md` as the storage format for now; the audit job writes it and the loader joins it. Report in the lesson view any audit row that matched no implication and any implication with no audit row.

Constraints. Keep the direct-API and Claude Code engines both working for every job (intake runs on both today). Jobs must survive a server restart in every status, as intake does. No new dependencies. Update `docs/configuring.md` and the README for the new jobs, the Research and Re-audit buttons and the override rule, and keep `server/src/docs.test.ts` green. Do not change the run pipeline (plan, contract, build, evaluate, wrap-up) or any component default.

Done means: a user can open an audit gap, press Research, read the findings on the Stage, start a run from them in a worktree, watch it pass evaluation, press Re-audit on the lesson, and see the gap's status flip to implemented with a citation, all from the UI, with every step recorded as events and recoverable after a restart.
